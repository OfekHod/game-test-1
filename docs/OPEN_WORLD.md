# Open World mode — implementation plan

**Status: plan only.** Nothing in this document is implemented. No game code changed in the commit that added it; the test build is identical to `main`.

## What was asked

An **Open World** mode beside Match and Survival, with ten requirements:

1. **Seeds.** Entering the mode assigns a random seed. The seed decides trees, bushes, rocks, rivers, lakes, forests, big mobs and even the birds; the same seed must reproduce exactly the same world.
2. **Endless.** Start with a world the size of the Survival arena; as any hero's sight nears the edge, generate what lies in that direction, and drop what is far away to save memory. The streaming algorithm should be native and simple, but work well.
3. **Minimap** still exists and shows the range around the focused hero.
4. **Forests come bulked.** A farming area mostly holds at least six camps, with the count random but fixed by the seed, so one seed has forests of different sizes.
5. **XP demand per level ×20** in this mode.
6. **No lanes, but dirt areas** with the lane's colour and feel: irregular, mostly ringed by seed-random bushes and rocks, holding one to three huge mobs roaming inside.
7. **A base tower at the middle** of the starting map; nobody attacks it for now.
8. **Medium mobs in forests.** Some camps hold one medium mob, some are all medium. The chance rises with distance: near the base almost only easy camps, very far away almost only medium ones.
9. **Bigger batches further out.** Forests grow with distance.
10. **Rivers** can be very long and change direction, all kinds, seed-random.

- The plan is written against `index.html` at commit `c75d7b3` (the game script is lines 2516–16732). Line numbers are given so a developer can jump straight to the code; they will drift as the file changes, so the function names next to them are the durable reference.
- §1 restates the ten requirements as testable statements. §2–§8 are the design. §9 is the mode-plumbing table (which of the existing `gameMode` branches the new mode inherits and which it extends). §10 is the test plan, including the determinism tests for the Node harness. §11 is the PR breakdown, the risks, and the **open questions with a recommended default for each** — those are the decisions the owner should confirm before implementation starts.
- §12 and §13 are the record of how the plan was produced: three candidate designs (architecture-first, content-first, determinism-first) were drafted independently, scored, and merged; the merge was then attacked by four adversarial reviews (determinism, performance, gameplay, UI and tooling) and two completeness passes. §13 lists every finding and what it changed. Where a finding was accepted with a different mechanism than the reviewer proposed, the row says so.
- Vocabulary: "easy mob" is today's camp neutral (70 hp); "medium" is today's big creep (880 hp) living in a camp; "apex" or "huge" is today's roaming giant (1760 hp); "grove" is a bulked forest of camps; "dirt area" is the packed-earth clearing the apexes roam.

## 1. Goals & non-goals

| # | Requirement | Testable statement |
|---|---|---|
| 1 | Seeds | `startRound('openworld', S)` twice → `world.hash()` identical; `S+1` → different. Trees, bushes, rocks, rivers, lakes, dirt areas, groves, camp counts and rosters, apex counts, gravel and the bird schedule are all functions of `S`. Zero `Math.random` calls occur inside generation (poison test throws otherwise), and a chunk built in isolation hashes identically to the same chunk when it streams in during play. |
| 2 | Endless | The first round builds the 4×4 chunks covering today's `[0,4000)²` Survival box. A chunk is built before any hero or the camera can see it, dropped when farther than `UNLOAD_R` from every hero and the camera focus, and a re-entered chunk has the identical `chunkHash`. The loaded set always contains the wanted set (no eviction of a wanted chunk; a soft warning at 120). Baked tiles live in a pool sized from the view (≈ 62–71 tiles desktop, 32–36 phone); the 64 MB `bgCanvas` is released for the round, so canvas memory is ≤ today's + 8 MB on desktop and half of today's on the phone. |
| 3 | Minimap | A window sized from the view (**A1**) centred on the driven hero, obeying vision with memory (**A4**); camps, water, dirt areas, allies, viewport; rim markers with bearing for the base and for any ally outside the window. |
| 4 | Bulked forests | Camps come in groves; a grove holds `n` camps drawn from its own stream (≥ 6 in ~82 % of groves at the home ring, 100 % beyond 61,800); two groves under one seed differ in count and roster. |
| 5 | ×20 XP | `xpForLevel(L)` returns `20·(20+(L−1)·8)` in Open World; unchanged elsewhere. |
| 6 | Dirt areas | Irregular packed-earth patches in the road palette, ringed by bush-trees and rocks with 2–4 real gaps, holding 1–3 apexes that wander inside the patch and are bounded to it. |
| 7 | Base | One main tower + plaza at (2000,2000); nothing attacks it; heroes base-regen there; respawn rule in §6.1. |
| 8 | Medium mobs | Per camp, 0 / 1 / 2 / all slots medium; `pTouched` 2 % at 1500 units → 100 % at 91,500. "Harder" means the medium reaches a max-range hero and heals if kited (§6.3). |
| 9 | Bigger batches | Camp count per grove rises 6.5 → 10 with distance; camp size 3 → 4–5; grove radius grows with count. |
| 10 | Rivers | Random walks 2,500–12,000 long with drift, curl and sharp elbows; one object per river (by `id`) held by every chunk it crosses, so no seam can disagree. |

**Out of scope "for now":** enemy heroes and anything attacking the base (Survival's dead-team recipe reused verbatim); allies farming on their own (they follow and auto-attack as in Survival, and — new — auto-spend their stat points); persistence across page loads (the diff store lives for one round); seeding Match/Survival/Tutorial terrain (their generators stay on `Math.random`, so the README "Known state" table is untouched); a mode-specific music theme; multiplayer.

## 2. Seeds & determinism

### 2.1 Seed source and UI
- `worldSeed` (new `let`, int32). `startRound(mode, seed)` (15519): for Open World the seed is **required** — `if(mode==='openworld' && !Number.isInteger(seed)) throw new Error('openworld needs an integer seed')`. Every caller passes it explicitly (title button, "Play this world again", Play Again, the harness); `pendingSeed` is only ever written by the title button. Under Node a forgotten argument therefore throws instead of quietly generating seed 0. **The UI chain carries the seed end to end:** every button start goes `guardedStart(mode, seed)` (15702) → `beginRoundLoad(mode, seed)` (15726) → the double `requestAnimationFrame` → `startRound(mode, seed)` (15790); both functions gain the second parameter and pass it through untouched (`undefined` for Match, Survival and Tutorial, which ignore it). `restartBtn` (15863) calls `guardedStart(lastMode, worldSeed)`; the keyboard Enter shortcut (15860) stays `guardedStart('regular')`. Without this the throw at 15790 would fire on every Open World start from the UI.
- **Seed entry ships in PR2, not PR6.** A small `<input id="seedInput" inputmode="numeric" placeholder="seed (blank = random)">` positioned absolutely **under** `.menuBoard` (outside it, own CSS: the painting's fixed box at 592–594 is untouched, and 626–629 already only just holds three buttons). Read by the Open World button: `pendingSeed = (parseInt(seedInput.value,10)|0) || (Math.random()*0x7fffffff)|0; guardedStart('openworld', pendingSeed)`.
- **One rule for the box: the button reads it, and every start empties it.** At the end of `startRound` (Open World) `seedInput.value = ''` and `seedInput.placeholder = 'seed (blank = random) · last world ' + worldSeed` — the seed you are in is visible in the grey placeholder (and on the loading/pause panels), but a blank box means "random", so two Open World starts in a row on one page load give two different worlds, and a seed the player typed (or pasted from the pause panel's tap-to-copy) gives that world. There is no `dataset.typed` bookkeeping: a non-empty box is by construction something the player put there (or the URL, once — next bullet). Replaying the current world without retyping is the pause panel's job ("Play this world again"). Verified by hand in PR2's screenshot pass (§10.5): start → pause → Leave → start shows a different seed on the loading panel; typing the first seed shows it again.
- **The URL seeds the input once.** `seedFromUrl()` is a *function* reading `location.search` at call time (`typeof location` guard as `FF` 14070, but not file-only — a seed must be shareable from an http link): on page load `seedInput.value = seedFromUrl() ?? ''`. The URL is not consulted again, and the first start empties the box like any other, so it cannot pin the button after the first world.
- **Address bar is best-effort only.** After the world starts: `try{ if(typeof history!=='undefined' && /^https?:/.test(location.protocol)){ const u = new URL(location.href); u.searchParams.set('seed', worldSeed); history.replaceState(null,'',u); } }catch(e){}` — preserves `?speed=`; explicitly a no-op on `file://` (Chromium raises a SecurityError on origin-`null` documents) and inside the artifact host (the address bar there is the host's). The **source of truth a tester copies is the seed text on the HUD/pause panel**, not the URL.
- **Replaying a seed has three routes:** the title input; **"Play this world again"** — a third button on `#pauseConfirmPage` (1026–1032), shown only in Open World, whose handler is exactly `tutQuit(); guardedStart('openworld', worldSeed);` — `tutQuit` (15276) tears the live round down first (`state = 'idle'`, dock and party hidden, `setPaused(false)` drops the pause overlay, `roundHold = false; loadingRound = false`, the title screen shown), so `guardedStart` then takes its ordinary title-screen branch and the world reloads exactly as from the title button; nothing is replaced mid-play and no second teardown path exists; and Play Again on the end card (`restartBtn → guardedStart(lastMode, worldSeed)` 15863, reachable only if `endRound` is ever called, §9). The title button always rolls a new seed unless the box holds one — and after a start the box never holds one unless the player typed it.
- Shown as text: loading panel (`<h1>`/`<p>` at 1138–1139 get ids; `beginRoundLoad` writes "Rolling a world" / "Seed 123456 · forests, plains, rivers…"), pause panel `#pauseResumePage p` (1023: "Seed 123456 · tap to copy" → `navigator.clipboard.writeText` guarded by `typeof navigator!=='undefined' && navigator.clipboard`), end card `#towerCompare` (1152).
- `startRound` resets **all** streaming state unconditionally, before `buildMap()`: `regionCache.clear(); riverCache.clear(); worldDiff = blankDiff(); loaded.clear(); genQueue.length = 0; owWarmQueue.length = 0; bgTiles.clear(); lastGenMs = 0; genCount.clear(); WX0=WY0=0; WX1=WORLD_W; WY1=WORLD_H; CAMX0=CAMY0=0; CAMX1=WORLD_W; CAMY1=WORLD_H;` — Open World's `worldInit()` then overrides the envelopes. A Match after an Open World round therefore starts on exactly today's clamps (test 7).
- **`OW_DEBUG` is parsed beside `FF` (14070), on any protocol.** `let OW_DEBUG = typeof location !== 'undefined' && /(?:^|[?&])owdebug(?:=|&|$)/.test(location.search || '');` — the same `typeof location` guard as `FF`, but **not** `file:`-only: the artifact is where the per-second readout (§10.4) and the `genDepth`/`SHADOW_REACH` asserts are needed, so `?owdebug` works on the published build too. Under Node `location` is undefined and `OW_DEBUG` is `false`, so the harness never pays for the asserts. It is a `let`, read at every use and cached nowhere: if the artifact host drops the query string, `OW_DEBUG = true` typed in the console turns the readout on for the rest of the page's life.

### 2.2 PRNG discipline
1. **Open World generation draws only from explicit streams; the ambient `genRng` is never set during generation.**
   ```js
   let genRng = null, genDepth = 0;
   function rand(a,b){
     if(OW_DEBUG && genDepth > 0) throw new Error('unseeded draw inside generation');
     return a + (genRng ? genRng() : Math.random())*(b-a);                       // 4629
   }
   function withRng(r, fn){ const prev = genRng; genRng = r; try { return fn(); } finally { genRng = prev; } }
   function ranged(rng){ return (a,b) => a + rng()*(b-a); }                      // a stream as a (lo,hi) draw
   ```
   Every `gen*` function takes `rng` and hands the leaf helpers `R = ranged(rng)` explicitly: **`makeTree(x,y,R)`** gains an optional third argument defaulting to `rand` (its two `Math.random()` at 4639–4640 become `R(0,1)`; Match calls `makeTree(x,y)` and is byte-identical). Open World never calls `makeLake` (4672 pushes onto the global `lakes`); the region layer builds `{x,y,r,sy,seed:R(0,6.283)}` records directly. `genDepth` is incremented around every region, river-layer, feature and chunk build, so a stray `rand()`/`Math.random()` inside generation throws in the `?owdebug` build and hits the poison in the Node test (with `genRng === null`, `rand()` calls `Math.random`, which test 3 replaces with a thrower).
   `withRng` is kept for exactly two uses: the bird schedule (item 6) and open question 14 (seeding Match later is one call away). The **eleven** direct `Math.random()` calls in the five live generator bodies are still converted to `rand(0,1)` for that reason — `makeTree` 4639, 4640; `scatterClumps` 5087, 5106; `buildCampRings` 5145, 5146; `scatterTrees` 5188, 5189; `scatterShoreTrees` 5245, 5261, 5277 — but **Open World's correctness does not rest on the conversion**: its generators are new functions with explicit streams. The twelfth, `Math.sqrt(Math.random())` at 5129, is inside the dead floor paint (overwritten by 6567 today) and is not ported as paint — §4 precomputes the floor from the camp's stream instead.
2. **Streams per concern, derived from (seed, salt, coords) — and string ids hash through `hashStr`:**
   ```js
   function hashInt(...ns){ let h = 0x811C9DC5|0; for(const n of ns){ h ^= n|0; h = Math.imul(h, 0x01000193); h ^= h>>>13; } return h|0; }
   function hashStr(s){ let h = 0x811C9DC5|0; for(let i=0;i<s.length;i++){ h ^= s.charCodeAt(i); h = Math.imul(h, 0x01000193); } return h|0; }   // FNV-1a, int32
   function streamFor(salt, ax, ay){ const r = mulberry(hashInt(worldSeed, salt, ax, ay)); r(); r(); return r; }
   const SALT = { river:1, region:2, ring:3, trees:4, shore:5, props:6, mottle:7, tufts:8, birds:9, plaza:10, stand:11 };
   ```
   `mulberry` (6714) exists. A chunk's loose-tree stream is `streamFor(SALT.trees, cx, cy)`; a region's is `streamFor(SALT.region, rx, ry)`; a river's `streamFor(SALT.river, rx, ry)`; a camp ring's `streamFor(SALT.ring, hashStr(camp.id), 0)`; a grove stand's `streamFor(SALT.stand, hashStr(stand.id), 0)`; a lake's shore `streamFor(SALT.shore, hashStr(lake.id), 0)`; a river's shore **segment** inside region `(rx,ry)` `streamFor(SALT.shore, hashStr(river.id+':'+rx+','+ry), 0)` — one stream per (river, region), named by the river and the region the segment lies in and by nothing else. Ids are strings built from the numeric tuple that names the feature (`'r'+rx+','+ry+':g'+gi+':c'+ci`), so `hashStr(id)` and the tuple name the same stream and nothing is drawn from another coordinate's stream; build order cannot change any output. Negative coordinates are fine (`|0`).
3. **Every feature-owned list is built exactly once and cached on its feature record.** A camp's ring lives on `camp.ring`, a grove's tree stands on `grove.stands[i].trees`, a dirt area's rim and gravel on the area record, a lake's shore trees on `lake.shore`, a river's shore trees on `river.shore` — a `Map` keyed by region key, one segment per (river, region), each built once from its own stream over the river points inside that region and dropped when that region is evicted — all on the region or river record that owns the feature, evicted with it (§3.5). Chunks only *filter* those lists; they never rebuild them. So two chunks straddling a lake read one array, whichever was built first.
4. **Generation reads no runtime state.** `nearWater` 4766, `onRoadway` 6956, `nearAnyTower` 4950, `decorSpotClear` 6849, `mixesWithNeighbour` 6885, `patchRoom` 6893 take an optional `lists` bundle `{lakes, rivers, camps, trees, props, dirt, towers}` defaulting to the globals. The Open World bundle's `towers` is the **constant `OW_TOWERS = [{x:2000, y:2000}]`**, never the live `playerTowers`/`enemyTowers` (4951 concatenates the live arrays — a chunk built before a round or after a Match would otherwise see different keep-outs than the streamed world). Generation never reads `timeLeft`, `performance.now()`, `camera`, the loaded set, or `bgCtx`. `spawnCamp` 9828 / `spawnApex` 9927 draw `atkCd:rand(0,0.5)` (9833/9929): they are runtime, run from `loadChunk(spawn=true)` in `chunkTick` **after** the build returns, and assert `genDepth === 0`.
5. **Unseeded, and why that is fine:** combat variance (`creepHitHero` 9853, `applyCreepHit` 12624–12695), `atkCd:rand(0,0.5)` at 9833/9929, apex waypoints and dwell (9915–9923, 9993), particles, level fx, shake, audio jitter, **clouds** (`cloudShapes` 7149 ← `buildCloudSprite` 7184 ← `makeCloud` 7239 ← `resetClouds` 7255 runs from `buildMap` at round start, so it *could* be seeded; it is left alone because a cloud is camera-relative decoration that `render()` never exercises under Node, so seeding it is untestable and buys nothing). Contract: **the world is a function of the seed; the fight is not.**
6. **Birds.** `birdRng = streamFor(SALT.birds,0,0)` set in `startRound` (Open World only). `spawnFlock` 8590 has **four** direct `Math.random()` calls — 8592 (species), 8596 (count), 8606–8607 (turn) — all become `rand(0,1)`; `updateBirds` wraps `withRng(birdRng, ()=>{ spawnFlock(); birdTimer = rand(4.5,12); })` (8620). **Draw before the readiness bail:** today `if(!birdReady) return;` (8591) precedes every draw, so a flock whose timer expires before the bird atlas decodes consumes nothing and the k-th flock's parameters would depend on decode timing. The Open World `spawnFlock` draws the whole flock record (species, count, angle, offsets, speed, turn, per-bird jitter) into a local first, *then* returns if `!birdReady`. The k-th flock's time, species, size, heading and curvature are then pure in game seconds whatever the phone's decode speed; where it appears follows the camera by design (8600). `dropBirdXp` 8585 stays unseeded. `birdReady` never becomes true under Node, so the harness cannot test birds; the seeded sequence is verified by eye (two runs, same seed, same first flock).

### 2.3 Known limits
`Math.sin/cos/atan2` are engine-defined in the last ulp; "same seed = same world" is guaranteed within one engine (Chromium and Node are both V8, so the harness hash equals the browser's). Safari may differ; documented in `docs/SIM.md`. `Map`/`Set` iteration order is insertion order; hashes sort keys explicitly.

## 3. World model

<!--fig:streaming-->

### 3.1 Coordinates
World coordinates are unbounded. The base stays at `(WORLD_W/2, WORLD_H/2) = (2000,2000)`, so the first 4×4 chunk block `[0,4000)²` is today's Survival arena in today's coordinates: `inBaseRange` 3517, `resetHero`'s `homeX/Y` 14094, the Survival hero offsets 15557–15559, `SURV_PLAZA_R` 2998 all keep working. `distBase(x,y) = dist(x,y,2000,2000)` is the difficulty axis.

### 3.2 Three grids, all derived from one number
- **`CHUNK = 1000`** — object ownership, spatial lists, load/unload. 4×4 = the start block. `cx = Math.floor(x/CHUNK)`, `key = cx+','+cy`. Features whose **extent** (§3.4) exceeds a chunk (a big dirt area reaches 1192, a grove 1370) are handled by bbox registration on every chunk the extent touches (§3.3), never by a 3×3 assumption.
- **`OW_TILE = CHUNK/2 = 500`** — baked background tiles, addressed as `(2cx+i, 2cy+j)`, so a chunk's 4 tiles are named from its key and no third addressing scheme exists (§4) — named, not held: tiles are keyed only in `bgTiles` and the chunk record has no tile field (§3.3, §4.1). Each tile's canvas is 504×504 — a 2-unit gutter on every side (§4.1).
- **`REGION = 4000`**, grid offset so the base sits at a region *corner*: `rx = Math.floor((x−2000)/REGION)`. The four regions touching the base are `(−1,−1),(−1,0),(0,−1),(0,0)`, each 4000² with the base at one corner. Why 4000 and not 2000: region features are confined inside their region by their full extent, and a 13-camp grove's extent is 1370 — a 2000 region would leave no core at all. At 4000 the core is 1220 wide for the biggest grove, 1798 for a 6-camp one, 2188 for the biggest lake.

### 3.3 What a chunk stores
```js
chunk = { cx, cy, key, x0, y0,
  trees: [], props: [], camps: [], stumps: [],      // OWNED: (x,y) inside this chunk; feature-owned lists filtered in
  lakes: [], rivers: [], dirt: [], groves: [],       // REFERENCES to features whose extent bbox touches the chunk
  hash: 0,                                           // FNV over the owned lists at build time, BEFORE the diff overlay
  pinned: false }                                    // no tiles field: tiles live only in bgTiles, keyed by tile coords (§4.1)
```
Every owned object carries `id` (`'r0,0:g1:c4'` for a grove camp, `'c3,2:t17'` for a loose tree, `'r0,0:g1:c4:b3'` for a ring bush, `'r0,0:g1:s2:t5'` for a grove-stand tree) and `chunk` back-reference. **The global `trees[]`, `props[]`, `lakes[]`, `rivers[]`, `camps[]`, `stumps[]` remain and are rebuilt as the concatenation of the loaded chunks' lists in `rebuildWorldLists()`** — rivers and lakes **deduped by `id`** (not object identity; §3.5 explains why identity is not enough) — which also nulls every tower's `_sightTrees` (12362) as `fellTree` does. `stumps[]` is the concatenation of `chunk.stumps`, so anything that makes a stump must push onto the chunk's list (§7). That is the minimal-diff decision: every runtime consumer in the terrain map §7 keeps its loop in the first streaming PR. **The chunk holds no tile references:** tiles are keyed only in `bgTiles` by tile coordinates (§4.1), `bakeTile(tx,ty)` reads the loaded chunks around the tile at bake time, and `bgTiles` alone says whether a tile exists — so loading or unloading a chunk touches no tile bookkeeping and a reload has nothing to re-link.

### 3.4 Layered, feature-owned generation (why both sides of a border agree)
Every layer is a pure cached function of `(worldSeed, coords)`; each layer reads only layers **above** it, never the same layer of a neighbour, so there is no cycle and no dependence on build order. **No layer reads outside the features registered on a chunk's 3×3** — that is what bounds the cost of building one chunk.

```
L0  rivers        per source region, streamFor(SALT.river,rx,ry)   reads: base keep-out only. NOT confined — a river crosses anything.
L1  region        per region, streamFor(SALT.region,rx,ry)         reads: L0 of regions within ±4. In this fixed order inside one stream:
                    lakes (1–3) → groves (1–3: camps, counts, rosters, floors, STAND CENTRES) → dirt areas (0–2: outline, rim, gravel, apex count)
                  every L1 feature is CONFINED: its EXTENT (below) lies inside the region.
L2  camp rings +  per camp, streamFor(SALT.ring, hashStr(camp.id), 0), built at region build, cached on camp.ring.   reads: L1
    grove stands  per stand, streamFor(SALT.stand, hashStr(stand.id), 0), built at region build in stand-index order,
    + lake shores   cached on grove.stands[i].trees.  reads: L1, the grove's rings, and the earlier stands of the same grove
                  per lake, streamFor(SALT.shore, hashStr(lake.id), 0), built at region build after the stands, cached on
                    lake.shore.  reads: L0 (river water, as a keep-out only), L1, the region's rings and stands, its own list
L3  river shore   per (river, region) SEGMENT, streamFor(SALT.shore, hashStr(river.id+':'+rx+','+ry), 0), over the river's
    segments        points inside region (rx,ry) only; built lazily once, when the first chunk of that region that registers
                    the river is built; cached on river.shore (a Map keyed by region key); dropped with the region (§3.5).
                    reads: THAT REGION's L1/L2 (lakes and lake shores, rings, stands) and its own list — never another
                    region and never another segment: trees are inset 75 from the region border (TREE_MIN_GAP/2), so two
                    segments of one river are ≥ 150 apart without reading each other. A mouth lake's shore points belong
                    to the segment of the region they fall in. O(points inside the region) per segment, once.
L4  loose stands  per chunk, streamFor(SALT.trees,cx,cy)           reads: L0–L3 of the features registered on the chunk's 3×3
L5  props         per chunk, streamFor(SALT.props,cx,cy)           reads: L0–L4
```
(Design note: shore trees were L4 "per feature reading L3 of every chunk the feature touches" in an earlier draft — that made the first chunk on a 12,000-unit river pay for ~25 chunks' stand recipes in one `genStep`. Swapping the layers makes a river's shore list a one-off O(points) job and keeps every per-chunk build inside its 3×3. Grove stands moved from L4 (per chunk) to L2 (per grove) in the final draft: a grove disc touches 4–9 chunks and no per-chunk rule could split `3 + n/2` stands between them without reading a neighbour's L4. River shores are per (river, region) segment in the final draft: one cached list per river would have read the L1/L2 of every region a 12,000-unit river crosses — four or more — and either forced those regions to build synchronously, breaking the one-region-per-frame rule and the 3×3 cost bound, or read whichever regions happened to be built, making the list depend on build order and failing test 3. A segment needs only its own region, which is already a prerequisite of every chunk inside it; lake shores moved up to L2 so a segment finds them built.)

- **Extent is one explicit number per feature, computed from its own recipe, and it is the single value used for the region inset, chunk registration and every lookup:**
  - grove: `0.92·R + CAMP_RING_R + 30 + TREE_MAX_R = 0.92·R + 225` (camps at ≤ 0.92R; ring bushes at ≤ 185 from a camp, 5148–5149; trunk r ≤ 40). Stand centres are drawn inside `0.92·R − 100`, so the stand spread (±285 at 5179/5191 + trunk 40 = 325) reaches at most `0.92·R + 225` — the same number. R = 930 → 1081; R = 1245 → 1370.
  - dirt area: `1.14 · DIRT_WOBBLE_MAX(1.46) · r + 60 = 1.664·r + 60` (rim slots at up to 1.14× the wobble radius, plus a rock's half-width or a trunk). r = 680 → 1192.
  - lake: `1.30·r + SHORE_TREE_GAP(40) + 7·26 + TREE_MAX_R = 1.30·r + 262` (the shore walk at 5266 steps out to 7·26 past the gap). r = 480 → 886.
  - river: `river.ext = w/2 + SHORE_TREE_GAP + 60 + TREE_MAX_R = w/2 + 140` from the centreline (5283 offsets up to 60). `riverBox` (4703, `w/2+2`) is kept for `inRiver`'s reject; registration uses a second cached box padded by `ext`.
- **Confinement replaces cross-region keep-outs.** A region's core for a feature is `[extent+20, REGION−extent−20]`; two regions' L1 features cannot collide because neither's extent leaves its region. Pairwise tests (lake–lake, grove–grove, grove–dirt) only ever run *inside one region's stream*. Loose trees, props and rivers fill across the borders, so the 4000 lattice is invisible.
- **Feature-owned, chunk-filtered lists.** A feature that straddles chunks (a grove's camps, ring bushes and stand trees; a dirt area's rim; a lake's shore trees; a river's shore segment for the chunk's region) is generated **once** from the feature's own stream as a complete list, cached on the feature; each chunk that has the feature registered keeps the members whose `(x,y)` fall inside it. Every member lies within the extent, so it lands in exactly one chunk and that chunk has the feature registered — the union of the chunks' filtered lists is the complete list with nothing lost or duplicated (test 4 asserts exactly this on features that really straddle a seam, a grove stand and a river's shore segments at a region border among them).
- **Chunk-owned things stay inside an inset — per object, not per patch centre.** Loose-stand patch centres are drawn in `[x0+75, x0+925]` (`TREE_MIN_GAP/2`) **and each tree of the patch is rejected by the existing `extra(x,y)` callback (5193) if it falls outside the same inset** — `scatterTrees` spreads trees ±285 from the centre (5179, 5191) with no bounds test of its own. Props inset 100 (> `t.r+60` worst case). Objects in adjacent chunks are therefore ≥ 150 apart without either knowing the other. `TREE_MIX_KEEP` 300 is not enforced across a seam (two stands of different silhouettes 250 apart across a border is acceptable).
- **Registration by extent bbox.** A lake is pushed onto `chunk.lakes` of every chunk its `1.30r+262` box touches; a dirt area onto `chunk.dirt` by `1.664r+60`; a grove onto `chunk.groves` by `0.92R+225`; a river onto `chunk.rivers` of every chunk its `ext`-padded box touches — so a point query at any position sees everything that can reach it in its own chunk's lists.
- **Confluences.** Two rivers may cross (§6.5), and each shore segment reads only its own river's water and its region's L1/L2 — never the other river's shore list — so at a crossing the two rivers' shore trees may stand closer than `TREE_MIN_GAP`, touch, or overlap. That is visual only: both lists are solid and sight-blocking as any tree, `resolveSolidCollision` pushes a hero out of both, and nothing else is placed against either list. It is not fixed by a cross-read on purpose: ordering the two lists would be an order over *built* rivers, which is build order, not a pure function of the seed, and would put the confluence's trees back on the wrong side of test 3. If a screenshot shows an ugly pile-up, the pure fix is a skip in the shore placer — reject a shore tree that lies `inRiver` of *any* river registered on the region (every river's water is L0 and pure, so the test is order-free) — which thins both banks at the crossing without either reading the other's trees.

### 3.5 Loaded window ("viewable sights"), bounded per tick
- **Wanted set:** chunks intersecting `hero ± LOAD_R` for every alive player hero (`LOAD_R = HERO_VISION 700 + CHUNK + 100 = 1800`: a whole built chunk lies beyond a hero's sight before he can reach its edge) ∪ the **camera's wanted box** ∪ the **pinned start block** (chunks 0..3 × 0..3 — never unloaded: base returns and the plaza bake are then always instant, and it is "the start of the generated map" the owner asked for).
- **The camera's wanted box is derived from the unclamped focus point, not from `camera`:** `focus = scout || dragPanCam || ride || drivenHero` (the same chain as 10943) → box `focus ± (W/2 + CAM_PAD, H/2 + CAM_PAD)`, `CAM_PAD = 300`, **plus the current camera box extended along its smoothed velocity by `|camV| · 0.6 s`** (`camVX/camVY`, 10972). A minimap scout (up to 2000 units out, glide 0.75 s at 8763–8766/9047–9050), a hero switch (0.38–0.82 s, 10835–10836) or an edge pan (`0.9·min(W,H)` u/s, 10843/10933) is therefore known to the loader the frame it begins, not after the camera has arrived.
- **`chunkTick()`** runs from `update()` every `CHUNK_TICK = 0.5` s **and immediately whenever the focus box's four corner chunk keys differ from the last tick's, or `scout`/`dragPanCam` is set** (four integer compares per frame). Node-safe, no canvas. It computes the wanted set; pushes missing chunks onto `genQueue` sorted by distance to the nearest hero/focus; unloads loaded chunks that are outside `hero ± UNLOAD_R (3000)` for every hero **and** outside the camera's wanted box + `CHUNK` (hysteresis of 1.2 chunks, so pacing on a border never thrashes). **A wanted chunk is never evicted.** There is no hard cap: with three heroes apart the wanted set is up to ~91 (3×25 + 16) and a chunk record is ~5 KB, so the cap bought nothing and cost a rebuild every tick; `OW_LOADED_WARN = 120` prints in `?owdebug` if exceeded. The tile pool (§4.1) is the real memory bound and is per camera.
- **`genStep()`** every `update()` frame drains `genQueue` under a **time budget**, not a count: `OW_GEN_BUDGET_MS = 6` normally, `12` while a tile inside the visible box is missing. Queue items are `{kind:'river'|'region'|'chunk'}`; a chunk item whose regions or rivers are not built yet enqueues them *ahead of itself* and requeues. **Exactly one rule is one-per-frame: a region build** (≤ ~8 ms desktop, §10.4). Everything else in the river layer is cheap and runs inline: a **"no source here" entry is one `rng()` draw on the region's river stream and is resolved inline, in unlimited numbers, during the ±4 scan** (81 lookups are ~81 hash + draw pairs, microseconds); a **river build** (≤ 20 walk steps, Chaikin ×2 over ≤ 80 points, ≤ 267 samples, ≈ 0.3 ms) is a queue item like a chunk, drained under the same time budget, as many per frame as the budget allows. A chunk's 3×3 spans at most 2 regions per axis, so a chunk entering a fresh region column waits for ≤ 4 region builds = ≤ 4 frames in the worst case — and normally 0, because `chunkTick` queues regions within 2200 of every hero ahead of need (below) and `LOAD_R` 1800 gives seconds of lead. Regions and river layers are pure, so their order is free. Then `rebuildWorldLists()` once if anything changed. Level-1 speeds are 171 u/s (tank: `SPEED_BASE` 100 + agi 63+8·1, `heroSpeed` 5683, `START_BUILD` 3183) and 227 u/s (carry/support, agi 127); walking straight, the frontier needs ~1 chunk/s and gets far more; a minimap scout 2000 out fills in over 3–4 frames instead of 30.
- Typical steady state with the squad together while walking: a 5–7 × 4–5 strip (36–64 chunks, since chunks leave at 3000 not 1800) plus the 16 pinned (mostly overlapping near home). §5 budgets for that, not for 25.
- **Regions** are cached in `regionCache`; `chunkTick` also queues regions within `MM_WORLD/2 + 200` of any hero (the minimap window's reach, §8; 2200 before **A1** widened the window, 3900 on a desktop after it) so `render()` never triggers a build (an unbuilt region draws as empty grass on the panel until it lands). Regions farther than 3 regions from every hero and the focus are evicted — all runtime state lives in `worldDiff` (§7), so eviction loses nothing; a region's feature records (rings, stands, rims, lake shores) go with it, and so does every river's shore segment for that region: the sweep calls `river.shore.delete(regionKey)` on each cached river, and the segment is rebuilt from its own stream, identically, when the region is next built (test 9).
- **Rivers are evicted by reference, not by distance.** A chunk registers rivers from source regions within ±4 (§6.5), so a river's source region can be 4 regions from a loaded chunk while the chunk still holds it. The sweep marks every river referenced by any loaded chunk and evicts only unmarked `riverCache` entries that are also ≥ 5 regions away (the "no source here" booleans too). A river's mouth lake is on the river record and goes with it; its shore segments have already gone with their regions (above), and any still cached on an evicted river go with the record. Combined with dedupe-by-`id` in `rebuildWorldLists`, `rivers[]` never holds two copies of one river (test 9).

## 4. Background rendering

### 4.1 A tile pool instead of one 4000² bake (Open World only)
- **`bgCanvas` is released for the round.** It is allocated 4000² at module init (2518–2519, `setupCanvas` 2569) and baked at page load when the third atlas decodes (`decorArrived` 6708–6712), before any round. Keeping it under a tile pool would double canvas memory, on the phone above all. So `startRound('openworld')` does `setupCanvas(bgCanvas, bgCtx, 1, 1, 1)`, `drawBackground` (6562) returns early in Open World, and **when `drawBackground` runs for any other mode and finds the canvas at 1×1 it re-runs `setupCanvas(bgCanvas, bgCtx, WORLD_W, WORLD_H, BG_DPR)` first** (Match's `buildMap` calls it anyway). `decorArrived` in Open World clears `bgTiles` (lazy rebake) instead of baking. `tutQuit` (15276) clears the pool and, if the mode was Open World, leaves `bgCanvas` at 1×1 until the next Match bake.
- **The pool is derived from the view in `applyLayout`, not a constant:**
  ```
  cols = ceil((W+504)/500)+1, rows = ceil((H+504)/500)+1        // a fractional camera shows one extra column/row
  OW_TILE_MAX = max(cols·rows + 8, openingTiles)                 // openingTiles: the tiles the start glide sweeps, below
  ```
  ≈ 62 on a 16:9 desktop (3373×1897: 9×6+8), 71 on the 16:10 headless viewport `shoot.js` uses (3200×2000: 9×7+8), 68 at 32:9, 32–36 on the phone (860×1861 either way: 4×6+8). Memory: 504² × 4 B ≈ 1.02 MB per tile → ≤ 72 MB on desktop against today's 64 MB `bgCanvas`, which is gone; 33–37 MB on the phone against today's 64. LRU by `used` frame, evicting farthest-from-camera first; **a tile inside the bake window is never evicted** (the pool is always ≥ window + 8). Tiles are keyed only in `bgTiles` (`tx+','+ty`) and a chunk record holds no tile references (§3.3), so a chunk load or unload changes no tile bookkeeping and a reload has nothing to re-link — the pool and the loaded set are two independent maps joined only by a tile's coordinates. Chromium keeps a GPU copy per accelerated canvas; with `bgCanvas` released the GPU side is the pool only. `?owdebug` prints `bgTiles.size / OW_TILE_MAX`. **The pool, its LRU and `bakeTick` ship in PR2 with the tiles themselves** — the bounded 4×4 world is 64 tiles against a 32–71 pool, so the moment tiles exist there must be on-demand baking and eviction (§11).
- **Gutter tiles, so seams are invisible at any scale.** The view canvas is scaled by `canvasScale` (2617: fractional, ≈ 0.81 on a 1300 CSS-px desktop at DPR 2, ≈ 0.73 on a 390-px phone at DPR 3) and translated by the fractional `camera.x/y` plus shake (13582–13584), so a tile edge always lands on fractional device pixels and would be bilinear-sampled on its own — two adjacent partial-coverage edges over a cleared canvas composite to a hairline every 500 units. So each tile is a **504×504 canvas** baked with `setTransform(1,0,0,1, 2−tx·500, 2−ty·500)` and blitted `ctx.drawImage(tile.canvas, tx·500−2, ty·500−2)`: neighbours overlap by 4 world units of **identical world-space pixels** (every straddler rule in §4.2 draws the same thing on both sides), so no tile edge is ever exposed. The 500 grid and addressing stay. Snapping the camera alone would not help at a fractional scale. The seam close-up in §10.5 is taken at `canvasScale ≠ 1` and on `--phone`.
- **`bakeTile(tx,ty)`** runs from `render()` only, never `update()` (Node never renders; `document.createElement('canvas')` stays off the update path). **`bakeTick()` works under the same time budget as `genStep`** (6 ms, 12 ms when a visible tile is missing; ≈ 2 ms per tile: 121 ms / 16 M px, FINDINGS 199–205), nearest the camera first within the bake window `focus box ± 250`, then draws 1 px of each so Skia rasterises it before it is visible. A wanted-but-unbaked tile is filled `GRASS_COLOR` (never a hole).
- **Opening bake.** `startRound` parks the camera at (0,0) and glides 1.15 s to the hero at (2140,2000) (15555), and `update()` is held behind the panel (11053), so the panel frames bake the tiles nearest (0,0) and the destination view would be half unbaked when the glide arrives — at headless ~10 fps that is the whole glide, and the first screenshot of every seed would show grass popping in. So **the union of the start view and the destination view is baked synchronously in the first `render()` after `roundHold` is set** (15791; the panel holds for `WARM_FRAMES` 8 frames and `LOAD_MIN_MS` 3000 ms, 15658, so the bake is hidden either way): 8×6 = 48 tiles on the headless desktop (~100 ms), 6×6 = 36 on the phone portrait (~200 ms), both ≤ `OW_TILE_MAX` by construction (`openingTiles` is the second term of the max). **`startRound` creates no canvas:** it only records the two boxes as `owOpeningBoxes = [startBox, destBox]` (`?warp` records the warped boxes instead, §10.5); the first `render()` consumes and nulls the record, bakes every tile the boxes cover, then `bakeTick` takes over. `startRound` is also the harness's Node entry (test 1), and a bake there would create 48 canvases against the stub on every sim start — the one place the opening bake runs is `render()`, like every other bake. The tile count is printed in `?owdebug`. This synchronous set is PR2 too (the glide exists from the first playable build).
- **No `drawBackground` refactor.** `const bgCtx` (2519) becomes `let bgCtx`; `bakeTile` points it at the tile's ctx with the gutter transform for the duration, so `bakeGravel`, `bakeShadow` → `softShadow` 6551 and the new `bakeDirt` draw **in world coordinates unchanged**, then restores it. Match's `drawBackground` body is byte-identical apart from the 1×1 guard.
- **Blit** (replaces 13590–13598 in Open World): loop `tx` from `floor((camera.x−shakeX−2)/500)` to `floor((camera.x−shakeX+W+2)/500)`, same for `ty`, drawing each tile at `(tx·500−2, ty·500−2)`.
- **Invalidation, with the reach computed from the bake:** `decorArrived` 6708 → `bgTiles.clear()`. A baked shadow is the `softShadow` ellipse (6551–6559: `rx/ry` *are* the extent — the gradient fades to nothing at the unit circle scaled by `rx, ry`, no further multiplier). For a tree (6817) `rx = 0.23·dw`, `dw = r·k·sc·DECOR_SCALE` (4651, 6652) → max `40 · 3.05 (frame 9, 6626) · 1.16 (4640) · 2.5 = 354` → `rx ≈ 81`, drawn at `y + 0.20·r` (+8) with `ry = 0.082·dw ≈ 29`; for a prop (6813) `rx = 0.42·w`, `w = k·jit·DECOR_SCALE` (6920) → rock max `66.3 · 1.24 · 2.5 ≈ 206` → `rx ≈ 86`, bush max `55.3 · 1.28 · 2.5 ≈ 177` → `rx ≈ 74` (dirt-rim rocks use the same 0.78–1.24 jitter). So **`SHADOW_REACH = 100`** (the rock's 86 rounded up; a computed constant next to `bakeShadow` with this derivation as its comment, and a `?owdebug` assert that no baked ellipse exceeds it). When a chunk loads, **every tile of its 8 neighbours whose bbox comes within `SHADOW_REACH` of the new chunk's box is marked dirty** (a tile whose neighbour chunk was missing at bake time lacks that chunk's border-tree shadows for up to ~90 units), and `bakeTick` re-bakes dirty tiles nearest-first. Unloading a chunk does not touch tiles. **A felled tree takes its shadow with it — decided, not left to chance:** a rebaked tile reads `chunk.trees` after `applyDiff` and so has no shadow at a stump, and rather than let a cached tile disagree with a rebaked one, `fellTree` marks dirty every tile whose bbox meets the felled tree's shadow ellipse (one to four map lookups; the rebake lands within a frame or two under the budget, while the trunk is still going over). Match's `bgCanvas` is never rebaked and keeps the shadow, as today; that is a Match property, not this mode's.

### 4.2 What a tile bakes and how seams stay invisible
Everything is drawn through the world-space transform, so a shape crossing a tile edge (or its 2-unit gutter) is drawn identically by both tiles and clipped by the canvas.

| Layer | Source | Seam rule |
|---|---|---|

| 64 px grain pattern (6576–6584) | one pattern source canvas built once at module init from `mulberry(0x51EED)`, `createPattern` per tile ctx | a pattern is anchored to the context's transform origin = world (0,0), so the repeat is continuous whatever the tile size or gutter |

### 4.3 Skia warm-up for water that appears mid-play
`drawWater` costs 21 ms/frame for ~100 frames after a fresh river is first rasterised (15672–15680; the comment there is exact: "the only thing that warms a raster cache is rasterising"). With no load panel to hide it, a river entering the load window would hitch mid-play, and in Open World that recurs for every river that enters the window. **`warmRoundCaches` 15837 does not solve this and an earlier draft misread it:** its body (15838–15848) builds JS-side caches only — `riverPoly`, the `Path2D`s, `riverBands`, `riverArc`, `lakePath` — and issues no stroke, fill or clip of water; today's raster warm-up is the eight full frames drawn behind the panel (`WARM_FRAMES` 8). A stroke inside a 1×1 clip rasterises one pixel and warms nothing.
So the warm queue **rasterises at real size, on the main canvas, before the frame's clear:** `render()` begins with `ctx.clearRect(0,0,W,H)` (13577); when a chunk load adds a river or lake not yet warmed it is pushed onto `owWarmQueue`, and each frame `render()` first — under the real `canvasScale` transform, translated so the feature lands on-screen — draws one stage of the head item (frame 1: sand stroke + shallow fill; frame 2: the 14 band strokes; frame 3: caustics + outline; a lake: its three `lakePath`s and gradient), *then* clears and draws the frame. The pixels are erased; the rasterised paths and patterns stay cached at the scale they will be drawn at. No scratch canvas, no memory. Water enters the load window ≥ 1100 units before it can be seen, i.e. seconds before its first visible frame. §10.4(c) measures it with and without the queue; **the honest fallback if the cache does not transfer:** accept the ramp and halve `drawWater`'s work for a new river's first 100 frames (`RIVER_BANDS` 14 → 7 for that river, `rv._warmFrames`).

- **Where:** 0–2 per region (`P(0)=.45, P(1)=.40, P(2)=.15`), never `D < 2200`; centre inset `extent+20` with `extent = 1.664·r + 60` from the region edge; reject on `nearWater(extent)` or within `extent + groveExtent + 200` of a grove of this region.

### 6.5 Rivers (req 10) — pure, order-free, and unsliced
A river is **a pure function of its source region**; no chunk ever extends one, it only asks "which rivers cross me?". From `rng = streamFor(SALT.river, rx, ry)`:
```
has source: rng() < OW_RIVER_P (0.7)            (region (0,0) always, as the home river, §6.1)
source uniform in the region, REDRAWN while distBase(source) < 1700 — up to 20 draws; only the four base regions can
  reject at all (every other region lies wholly beyond 1700), and the rejected quarter-disc is 14 % of a base region,
  so 20 failures do not happen in practice (if they did, the region has no source); heading h uniform
  (the home river is the exception, §6.1: source fixed at D = 1300 in region (0,0), heading away from the base,
   so every step increases D and the `< 1100` stop can never fire on it)
L = 2500 + 9500·rng()^1.6   (median ≈ 5,600, max 12,000);  w = 120 + 60·rng();  wob = 25 + 35·rng()
curl c = (rng()−0.5)·0.14 rad/step        — some rivers arc for miles
per step of 600 units:
  h += c + (rng()+rng()−1)·0.5            — triangular drift, sd ≈ 0.2 rad
  with p = 0.10: h += ±(0.6..1.0)         — a real elbow
  stop when the budget is spent or distBase(next) < 1100
control points → Chaikin ×2 → sample every RIVER_STEP 45 → the makeRiver sine wobble (4697) at amplitude wob along the normal
with p = 0.45 the river ends in a mouth lake { id, r: 240+160·rng(), sy, seed } owned by the river layer
→ { id, pts, w, mouth, ext, bx0..by1, segBox[], shore:null }   — the shape inRiver, flowAlign, drawWater already consume
```
- **Which rivers touch a chunk:** `RIVER_MAX_LEN 12,000 / REGION 4,000 = 3`, so scan source regions within ±4 of the chunk's region — 81 lookups, each either a cached river object, a cached "no source" boolean, or **the first `rng()` draw of that region's river stream, taken inline** (a boolean is one draw and one Map set; the whole scan is microseconds). Only a region that *has* a source and is not yet built becomes a `genQueue` river item, drained under the time budget (§3.5). Each river whose `ext`-padded box touches the chunk is pushed onto `chunk.rivers` (its mouth lake onto `chunk.lakes`). **Every chunk holds the same object**, `rebuildWorldLists` dedupes by `id`, and the river is evicted only when no loaded chunk references it (§3.5) — so `riverPoly`/`riverPath` caches build once, both banks of every seam are one polyline, `drawWater` never strokes one river twice, and no open-end polygon variant of `riverPoly` is needed. Region lakes keep `nearWater` off the layer's rivers and mouth lakes (pad 60).
- Rivers may cross each other (a confluence in the same colours reads fine; rejecting would make regions depend on each other's river stage). ~0.7 sources per 16 M with 5,600 average length ≈ one crossing per ~2,500 units of travel.
- Cost: a 12,000-unit river is 267 points; culled by its tight `riverBox` against the camera box, foam/flow skip off-screen points, and PR5 strokes only the on-screen stretches (§5). ### 6.8 XP ×20 (req 5) — the arithmetic

One convention for the table: **"step to leave L" is `xpForLevel(L)` = `400 + 160(L−1)`**, and **"cumulative to reach L"** is the sum of the steps below it, `400(L−1) + 80(L−1)(L−2)`:

|---|---|---|---|
| 1 | 400 | 0 | 0 |
| 2 | 560 | 400 | 4.2 |
| 5 | 1,040 | 2,560 | 27 |
| 10 | 1,840 | 9,360 | 98 |
| 15 | 2,640 | 20,160 | 210 |
| 20 | 3,440 | 34,960 | 364 |
| 26 | — | 58,000 | 604 |

**Income, and what levels actually buy.** Basic damage is fixed per type and never scales — `heroBasicDmg` 5686 returns `FIXED_DMG` (3139: carry 38, tank 52, support 13; the 3131–3138 comment says why, and the "42" at 2955 is stale). What a level buys is **mana**: `STAT_SCALING` maxMana +10 and manaRegen +0.7 per point (3166–3170), and a swing costs mana (tank 7, carry 4, support 2; 3207; gated at 9402). At level 1 that is: tank 70 mana / 2.7 s⁻¹ → 10 swings (520 dmg) in 11 s, then one every 2.6 s (20 dps); carry 90 / 3.4 → 22 shots (836 dmg) in 4.4 s, then 32 dps; support 120 / 6.9 → unlimited at 26 dps. Party burst ≈ 1,750 in ~11 s, then ≈ 78 dps sustained, refilling in ~25 s of standing about.
- An easy camp is 3 × `NEUTRAL_XP` 32 = 96 xp and 210 hp: two tank hits per mob, ≈ 6–8 s per camp plus ~4 s walking 510 units between rings → **~10 s/camp, 576 xp/min ceiling** while the mana lasts, with `NEUTRAL_RESPAWN` 15 s < a 6-camp lap so a grove never runs dry.
- An all-medium camp of three (2,640 hp, 480 xp) at level 1 is one burst plus ~11 s of sustained fire ≈ 22–25 s, then part of a refill: **~35–40 s per camp ≈ 700–800 xp/min** — above the easy ceiling at level 1, and it grows with levels because the pool and regen do (a tank at maxMana statLv 8 swings 15 times before dry). Far camps of 4–5 mediums (3,520–4,400 hp, 640–800 xp) take ~45–55 s at level 1 and are where a levelled party (bigger pools, the support's heal, allies auto-built) pulls ahead. Under the stretched span they are 3–9 minutes of walking out (§6.3), so the first trip to them is a decision rather than a detour; what keeps it from being a dead walk is that the medium share climbs the whole way, so a party farms itself outward instead of jumping tiers. Apexes (480) on top.
- **Income is split, not shared.** `collectXpOrb` (10406) grants to the collector only and `nearestCollector` (10318–10322) pulls each orb to the nearest hero within 130, so a three-hero blob divides the take. The table's per-level timeline — 2 at ~1 min, 5 at ~7, 10 at ~25–30, 20 at ~65, cap ~95–120 min — is the *party's* income landing on one hero, which only happens if the allies stand off. Realistic driven-hero pace is ½–⅔ of that: 10 at ~40–55 min, 20 at ~1.7–2.2 h, cap ~2.5–3 h, with every ally levelling on what it scoops. That is "farm much more" as asked; `OW_XP_MULT` is the one knob (§11 q.5), and sharing camp xp to the party is a listed alternative (§11 q.17).

**XP values by xp-per-hp** (why `XP_BIG_CREEP` 12 and `APEX_XP` 96 cannot be reused): easy 32/70 = **0.46/hp**; a medium at 96 would be 0.11/hp — a far all-medium camp would be a strictly worse farm than the home ring at every level. `NEUTRAL_BIG_XP = 160` (0.18/hp: an all-medium camp = 480 xp at level-1 parity, pulling ahead as mana grows, which is what makes walking out worth it) and `OW_APEX_XP = 480` (0.27/hp, five easy camps in one kill — the biggest fight is the best farm per hp, as it should be). Both are owner knobs (§11).

## 7. Runtime entities across load/unload — the diff store

Terrain is regenerated, never stored; **the player's history is a small overlay keyed by feature id**, applied on top of every load.
```js
worldDiff = { felled: new Set(),                       // tree ids
              camps:  new Map(),                       // id → { alive, timer, at }
              areas:  new Map() };                     // dirt id → { slots:[{alive, timer}], at }
```
`at` is `timeLeft` at save time (it counts up here, §9).

**Order, stated exactly:** `buildChunk` generates the pristine chunk — every layer reads pristine lists, so a felled tree still occupies its gap during placement and nothing shifts into its hole — then computes `chunk.hash`, **then** `applyDiff(chunk)` removes felled ids from `chunk.trees`, pushes their `{x,y,r}` onto `chunk.stumps`, and applies camp/area entries. `world.gen(cx,cy)` (§10.1) stops before `applyDiff`. Because L5 props were placed against the pristine tree list, nothing ever stands on a stump. A tile baked after the load reads the post-diff `chunk.trees` and has no shadow at the stump, which is the intended look (§4.1: `fellTree` dirties the tile so a cached tile agrees).

| Thing | Persist? | On unload | On reload |
|---|---|---|---|
| Felled tree | yes | nothing (`fellTree` 10617 adds `t.id` to `felled` when it splices, splices `t.chunk.trees` too, **pushes the stump onto `t.chunk.stumps`** — today it pushes onto the global `stumps` only (10630), and since `rebuildWorldLists` rebuilds `stumps[]` from the chunk lists on every chunk load, a stump pushed only onto the global would vanish the next time a chunk loaded, ~1 s later while walking — and dirties the tiles under its shadow, §4.1) | `applyDiff` skips the id and pushes `{x,y,r}` onto `chunk.stumps` (x,y,r are pure; only the id is stored) |
| Chopped-but-standing (`chops < TREE_CHOPS` 3) | **yes** (**A3**) | `worldDiff.chops.set(id, t.chops)` for every `t.chops > 0` in the chunk, scanned at unload | `applyDiff` restores `t.chops` and deletes the entry, so the map only ever holds chopped trees in chunks you are away from |
| `fellingTrees` mid-fall | no | finishes its 1.1 s wherever it is | — |
| Camp | yes | mobs with `n.camp === camp` spliced out of `neutralCreeps`; `camps.set(id, {alive, timer, at})` | `alive > 0` → `spawnCamp` (mobs heal to full at home anyway, 9905); `alive === 0` → `timer −= (timeLeft − at)`, spawn if `≤ 0` else keep counting |
| Apex slot | yes | mob spliced; `{alive: !!mob, timer}` per slot | alive → spawn now at a fresh patch point under the not-visible rule ("it roamed while you were away"); dead → timer continues |
| Wood drops, xp/mana/hp orbs, corpses, projectiles, particles | no | left in their global lists; they are ≥ 3000 units from any hero, culled by `onScreen`, and rot by `ORB_TTL` 15 / `WOOD_TTL` 30 | — |
| Towers, hero xp/levels/wood banked | hero/tower state, untouched | — | — |

`updateNeutrals`' recount (9874–9881) needs no `unloaded` flag: an unloaded camp is not in the rebuilt `camps[]` at all, so the 15 s ghost-respawn trap at 15543 cannot recur. Because a wanted chunk is never evicted (§3.5), a camp's `timer continues` semantics are never reset by loader churn. Play Again with the same seed starts with an empty `worldDiff`: a fresh copy of the same world — which is the owner's definition of "same seed = same world".

## 12. Decisions taken during synthesis

The plan was assembled from three independently written candidate designs, scored and merged. In the notes below, **Design 1** is the architecture-and-performance-first draft, **Design 2** the content-and-feel-first draft, **Design 3** the determinism-and-minimal-diff-first draft; **Judge 1/2** are the two scoring passes that ranked them, listed grafts and verified factual errors against the code.

- Spine = Design 3 (both judges' winner): scoped `genRng`/`withRng`, `lists` argument, feature-owned chunk-filtered lists, base at (2000,2000), `WX0..WY1` envelope (seven entity clamp sites; the three camera sites — `updateCamera` ×2 and `tutStart` — take `CAMX0..CAMY1`), `pendingSeed`, poison/leak/round-trip tests.
- `REGION = 4000` (not 2000) with the grid offset to put the base on a corner: Design 3's confinement rule is kept, and the inset arithmetic that emptied Design 2's core (and forced Design 3's fixed 620 radius) now holds a 13-camp grove — with the real extent (0.92R+225), a 1220-wide core.
- Grove count and radius from Design 2 (`6.5 + 3.5u + tri`) plus the per-grove bias (now faded in with distance), over Design 3's distance-blind `6 + floor(u²·5)`; `R = 660 + 45n` after the in-grove spacing moved to 510/660; Design 3's camp-size growth kept but softened to 3 → 4 (75 %) / 5 (25 %) far out.
- Grove tree stands are grove-owned (L2, centres inside `0.92R − 100`, one stream per stand keyed by `hashStr(stand.id)`) rather than placed per chunk — the only way `3 + n/2` stands can be split across the 4–9 chunks a grove touches without a chunk reading a neighbour's layer.
- **Difficulty span `(D − 1500)/90000`, ten times the first draft's 9,000** (owner review, O1): at 9,000 the full easy→all-medium ramp was 46–61 s of level-1 walking, so a fresh party could stand in all-medium terrain in its first minute and every distance past ~10 k was the same place for the rest of a multi-hour session. ## 14. Owner review: the six changed decisions

Written after the question-by-question review of §11. Each supersedes the sections it names; everything else in this document stands as written.

### A1 — The minimap window follows the view
*Supersedes §3.2's `MM_WORLD` figure, §8's first minimap bullet, and §3.5's 2200 region prefetch.*

A fixed 4000-unit window is right for a phone and close to pointless on a PC: the desktop view is **3373 × 1897 world units** (§4.1), so a 4000 window showed 1.19× the width already on screen, with the viewport rectangle filling 84 % of the panel. Everything else that scales with resolution is already derived from the view — the chunk wanted set is `focus ± (W/2 + 300, H/2 + 300)` (§3.5) and the tile pool is `cols·rows + 8` (§4.1) — so the window is the one thing left behind.

```js
MM_WORLD = clamp(2.2 * Math.max(W, H), 4000, 8000)     // ~7400 desktop, ~4100 phone either orientation
MM_W = MM_H = clamp(Math.round(MM_WORLD/20.5), 195, 300)   // panel grows with it, so dots keep their density
```
Units per panel pixel then rises only from 20.5 to 24.7, and a 10-camp grove stays ≈ 55 px across instead of collapsing to 36. **Region prefetch follows the window** (`MM_WORLD/2 + 200`, 3900 on a desktop) or the outer band of the panel would show unbuilt ground. `CHUNK`, `OW_TILE` and `REGION` are unchanged.

### A2 — No camp floor
*Supersedes the camp-floor row of §4.2's bake table, the "camp floors" clause of §1 req 1, and §12's graft note.*

The dead paint at 5168–5187 stays dead, in Open World as everywhere else. Camps are found by their ring, and the mode's packed-earth palette stays the plaza and the dirt bowls. No `camp.floor` record, no floor stream, and nothing for a tile to draw — which also means the twelfth `Math.random` (5180, inside the dead block) stays unconverted, as PR1 left it.

### A3 — Partial chops persist
*Supersedes the "Chopped-but-standing" row of §7.*

`worldDiff.chops: Map<treeId, chops>`. The entry is written **when a chunk unloads** — one scan of `chunk.trees` for `t.chops > 0` — and deleted when the chunk reloads and `applyDiff` puts the count back on the tree. So the map holds only chopped trees in chunks you are currently away from, rather than growing for the whole round. `barT` and `shakeT` are not stored; they are cosmetic and time-based. Like `felled`, it applies *after* `chunk.hash`, so hashes stay pristine and tests 3b and 5 are unaffected.

### A4 — The minimap obeys vision, with memory
*Supersedes §8's minimap bullet. Open World only for now; Match and Survival are reviewed once it has been played.*

Unexplored ground draws **blank**; ground you have seen draws **dimmed**; only what is inside current vision draws **live**. Vision is the existing system unchanged (`rebuildVision` 5429: heroes 700, player towers 520, ally creeps 380). A camp you have seen stays on the panel as a dim mark — "a camp is here" — and shows alive/dead only while it is in vision, so the panel stops being an oracle without becoming a black square. Your own heroes, the base marker and the viewport rectangle are always drawn; they are yours.

Mechanism: a **world-anchored low-resolution explored mask** (1 px ≈ 100 world units), re-centred as the window moves, with a soft disc painted into it at each vision source every frame. Draw the panel as §8 already specifies, then composite the mask over it: opaque where unexplored, partial where explored, clear inside vision. Ships with the minimap in **PR2**; if §10.4 measures the mask too heavy, the fallback is a plain clip to the current vision circles (cheap, no memory) and the mask moves to PR5.

`world.explored()` (km² seen) joins the harness surface in §10.1, since A5's card reports it.

### A5 — Quitting shows the session card
*Supersedes §9's `checkRoundEnd` row and the pause-confirm row.*

There is still no end condition — no clock, nothing attacks the base, death is a respawn (§6.1). But leaving a world now routes **pause → confirm → `endRound('quit')`** into the Open World card §9 already specifies, instead of straight to the title: "Explored" (from A4's mask), "Time in the world", `towerCompare` = "Seed N · Lv a/b/c · N xp looted", with Play Again on the same seed and Leave to the title. The card was being built for a path nothing reached; this gives it the one it was for. Copy is polished in PR6.

### A6 — No auto-spend, for anyone
*Supersedes §9's `grantXP` row and §6.7's ally auto-spend line.*

`grantXP` 6355 stays `if(h.side === 'enemy') aiSpendPoints(h)`, exactly as today — all three player heroes keep manual stat points in Open World as in every other mode, and the comment above that line ("The player spends their own team's points from the stat strip") keeps being true.

The consequence is worth stating where the design can see it: `recomputeStats` derives every stat from `statLv`, and a level grants only `h.points += 3`, so **an unspent level buys nothing** — an ally at level 20 with 20 unspent points fights as he did at level 1. With orbs going to the nearest collector within 130 (§6.8), most of a session's income lands on heroes the player must visit to convert. That is the intended shape — the hero you drive is your investment — so the only concession is a **reminder, not a shortcut**: a party chip whose hero holds ≥ 6 unspent points pulses, and spending is still done by switching to him. The reminder lands in PR6.

## 15. First build: three things the owner walked into

PR4's first build was played for ninety to a hundred thousand units and came
back with two reports — no bowls anywhere, and "the game crashed in the
distance". Both were real, and finding the second one found a third.

### F1 — Bowls could almost never be placed
*Amends §6.4's placement rule.*

A bowl wants its whole radius clear of water, and its extent (1.664·r + 60, up
to 1190) inside the region's core, which leaves a placement box of 1618–2680
units in a 4000-unit region that usually has one to three lakes in it and
sometimes a river through it. Measured: **90 % of attempts died on water, and
ninety-two regions of walking produced two bowls.** The fix is to ask for less
rather than for nothing — the requested radius is tried, then 0.8, 0.64 and
0.512 of it down to `OW_DIRT_MIN_R` 300, 60 attempts each. Same rule, same
keep-outs, a smaller bowl. Placement now succeeds 25 times in 28, and the same
walk goes past **50 bowls instead of 2**. Test 15 pins it.

### F2 — A giant outlived its bowl
*Amends §7's diff-store table.*

`unloadChunk` culls the mobs of the camps in that chunk. A giant belongs to a
**bowl**, which spans several chunks, so nothing culled it: a walk of 136,000
units ended with twenty-two giants alive and roaming ground that had been
thrown away. The cull belongs in `rebuildWorldLists`, where the live bowl list
is rebuilt — a giant whose `area` is no longer in it goes, and its slot is told
it was *unloaded* rather than killed (`timer = 0`, not `OW_APEX_RESPAWN`), so
the bowl has its giant again when you walk back in. Test 15 pins it.

### F3 — Holding one direction could stop the hero for good

Not a PR4 bug, and not a crash: a prop blocks along a **bar** at the foot of its
sprite (§5 of `index.html`'s prop notes), and two bushes whose bars overlap make
a notch whose two constraints push back exactly as fast as you walk in. The
hero stops dead, with no error and no way out for as long as the key is held.
Reproduced in Node at (79 780, 1 832) on seed 42 walking east, and again
between two trees; a player sees the game freeze.

In a match you steer every second and would never meet it. In the open world
the whole loop is "point yourself east and hold it", so it had to go.
`steerAroundStall` sits between the keys and the velocity: when the direction
asked for last frame did not happen, it turns the request off the obstacle a
little further each frame (`SLIP_TURN`), keeps one side for the whole detour so
the hero cannot saw himself backwards, tries the other side if fully deflected
and still stuck (`SLIP_JAM`), and straightens up once he is past it. The AI
never touches this path — it steers itself — so nothing in `sim/run.js` moves.
Eight two-minute walks now cover 82–100 % of open ground with a longest stop of
1.5 s. Test 17 pins it.

## 16. PR5: what the measurement said, and what it retired

§10.4 named the numbers to take and §11 listed the optimisations to make from
them. The numbers came out differently from the plan, so most of the list is
retired rather than shipped — each one below with the measurement that retired
it. `docs/FINDINGS.md` has the tables.

**The readout first.** §10.4(a) is now printed in full by `?owdebug`: frame
total split into `update` and `render`, the **worst frame of the second and
what it paid for** (bake / chunk / region), tile blits, `resolveSolidCollision`
calls a frame, the largest fog near-set, ground sprites drawn, and the heap
where the browser exposes it — plus `drawFog` broken into carve / sheet / blur
/ out, which is what found the one change this PR makes.

**The one change: `FOG_SCALE` 0.8 → 0.5.** The fog is 21 of a 33 ms frame, and
19.6 of those 21 are the blur and the stretch — both per *source* pixel, so the
surface is the lever. Three interleaved pairs: **34.3 / 33.5 / 35.1 ms against
19.9 / 20.4 / 20.4**, worst frame 54 → 32, and the pictures are the same one at
the base and inside a nine-camp grove. FINDINGS' "that one is visible" was a
guess; it is now a measurement that says otherwise.

**Retired, with the number that retired it:**

| §11 item | Measured | Verdict |
|---|---|---|
| `segBox`, per-stretch river sub-paths (§5, §10.4c) | water draws in 0.1–0.3 ms with three rivers on screen | nothing to cut; `rv._path` from PR3 was already enough |
| minimap `_path` stroke | minimap is 0.85 ms | already cheap |
| `forChunksAround` narrowing | **3** `resolveSolidCollision` calls a frame (mobs outside `CAMP_TICK_R` do not move) | unnecessary, for a second reason on top of the 0.15 ms the last pass found |
